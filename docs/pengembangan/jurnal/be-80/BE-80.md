## Niat

- Tujuan: Menambah migrasi `public.weather_forecasts` yang kolom, kunci, dan indeksnya mengikuti penulisan `POST /api/weather/refresh` dan pembacaan cache. RLS: anon dan authenticated hanya SELECT. Tulis hanya lewat service role. Tidak menerapkan apa pun ke basis data hidup. Tidak mengubah jadwal, env, atau perilaku workflow.
- Berkas:
  - `supabase/migrations/20261028_weather_forecasts.sql` (baru)
  - `src/lib/weather/weather-forecasts-migration.test.ts` (baru)
  - jurnal ini
  - satu baris `docs/pengembangan/STATUS.md`
- Tidak diubah: `weather-refresh.yml`, env, fixture, UI, rute, `20260824_weather_forecasts.sql`, basis data hidup.
- Langkah:
  1. Turunkan kolom dari objek upsert di route dan dari `select` pembaca.
  2. PK `kabupaten_kota` karena route tidak mengirim `onConflict` (PostgREST memakai primary key) dan skrip cache mengirim `onConflict: "kabupaten_kota"`.
  3. `expires_at timestamptz` plus indeks pada kolom itu.
  4. RLS select-only, kebijakan dijaga, tanpa kebijakan tulis untuk anon/authenticated.
  5. Uji statis kolom migrasi versus kunci upsert. Lalu `npm test`, `tsc`, `lint`, `build`.
- Cara membuktikan: uji berkas; log perintah. Tidak ada `db push`, SQL editor produksi, atau POST refresh.
- Risiko: Berkas `20260824` sudah ada di repo. Menerapkannya setelah berkas ini gagal pada `create policy` yang tidak dijaga. Workflow saat ini tidak menulis cache; mengisi variabel URL adalah langkah pemilik, di luar PR ini.

### RLS

- `enable row level security`.
- Satu kebijakan `weather_forecasts_select`: `for select to anon, authenticated using (true)`. Dibuat di dalam `do` hanya jika `pg_policies` belum punya nama itu (nama yang sama dipakai `20260824`).
- Tidak ada kebijakan insert, update, atau delete.
- `revoke insert, update, delete` dari `public`, `anon`, `authenticated`.
- `grant select` ke `anon`, `authenticated`.
- `grant select, insert, update, delete` ke `service_role`. Role itu yang dipakai route (`SUPABASE_SERVICE_ROLE_KEY`, `route.ts` baris 49–56). Di Supabase, `service_role` melewati RLS. Tidak ada `force row level security`, supaya jalur tulis cron tidak terkunci.

Kueri verifikasi dan rollback ada di berkas migrasi sebagai komentar. Bukan perintah yang dijalankan tiket ini.

## Akar galat refresh

Workflow `.github/workflows/weather-refresh.yml` tidak diubah.

Saat run jalan:

1. Pemicu: cron `0 */3 * * *` (UTC) atau `workflow_dispatch`. Izin `contents: write`.
2. Job `refresh-snapshot` mengambil kode, Node 20, menjalankan `node scripts/build-weather-snapshot.mjs`, lalu commit `public/fixtures/weather-snapshot.json` bila berbeda. Job ini tidak menyentuh Supabase.
3. Job `refresh-supabase` bergantung pada job pertama dan hanya dibuat bila `vars.WEATHER_REFRESH_URL` tidak kosong.
4. Bila job itu jadi jalan: env `WEATHER_CRON_SECRET` dari `secrets.WEATHER_CRON_SECRET` dan `WEATHER_REFRESH_URL` dari `vars.WEATHER_REFRESH_URL` (nama saja). Jika secret kosong, langkah menulis pesan nama variabel saja (tanpa nilai) dan `exit 1`. Job merah. Sebelum perbaikan ini langkah yang sama memakai `exit 0`, jadi job tetap sukses. Jika secret ada, `curl -fsS -X POST` ke URL itu dengan header `Authorization: Bearer` dan `Content-Type: application/json`. `curl -fsS` menggagalkan langkah pada HTTP non-2xx.
5. Route `POST` (`src/app/api/weather/refresh/route.ts`, alias `src/app/api/cron/weather/route.ts`): tanpa `WEATHER_CRON_SECRET` di aplikasi membalas 503; Bearer salah membalas 401; URL atau `SUPABASE_SERVICE_ROLE_KEY` kosong membalas 503. Perilaku 401 dan 503 itu tidak diubah. Pada jalur itu `curl` menggagalkan job dengan keras.
6. Pada jalur tulis, route membaca `{ error }` dari setiap upsert. Bila ada error, `console.error` mencatat `kabupaten_kota`, `code`, dan `message` saja, lalu balasan 502 `{ ok: false, error: "upsert_failed", failed }` dengan `failed` = jumlah upsert yang gagal. `revalidateTag` tidak dipanggil pada jalur itu. Sebelum perbaikan ini error diabaikan dan balasan tetap 200, jadi `curl -fsS` sukses walau baris tidak tertulis. Jalur semua upsert berhasil tetap 200 `{ refreshed, providers, expires_at }`.

Pembacaan produksi memakai klien anon (`createServerClient` di `src/lib/supabase/server.ts`). `loadFromSupabase` (`service.ts` baris 146–151) mengembalikan null bila kueri error atau kosong, lalu `getWeatherForecasts` mengunduh BMKG / Open-Meteo. Itu sebab kartu jatuh ke unduhan langsung selama tabel belum ada.

### Dikerjakan

Koordinator menyetujui dua butir ini pada draf yang sama. Jadwal `0 */3 * * *` dan syarat job `if: ${{ vars.WEATHER_REFRESH_URL != '' }}` tidak diubah. `curl -fsS` tetap.

1. Bila `WEATHER_REFRESH_URL` terisi tetapi `WEATHER_CRON_SECRET` kosong, langkah `refresh-supabase` menulis pesan nama saja dan `exit 1`. Nilai secret tidak dicetak.
2. Route menghitung upsert yang mengembalikan `error`. Ada gagal: HTTP 502 `{ ok: false, error: "upsert_failed", failed }`. Semua berhasil: HTTP 200 bentuk lama. Rincian SQL hanya di `console.error`.

### Masih di luar kode

Nilai yang sudah tertulis di `docs/vercel.md` adalah URL produksi `POST /api/weather/refresh` (alias `/api/cron/weather` juga sah). Secret yang dipakai tetap `WEATHER_CRON_SECRET`. Jangan menulis nilainya. Bila URL terisi dan secret masih kosong, job sekarang merah, bukan sukses diam.
