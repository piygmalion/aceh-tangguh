## Niat

- Tujuan: Jadwal GitHub `overlay-live-refresh.yml` (`*/15`) sering terlambat 2–6 jam, sementara baris overlay kedaluwarsa setelah 2 jam (`OVERLAY_WEATHER_LIKE_TTL_MS`). Kartu live jadi tidak tersedia di antara jalan. Penjadwal primer pindah ke `pg_cron` di Postgres, setiap 15 menit, memanggil `POST https://aceh-tangguh.vercel.app/api/cron/overlay-live`. Workflow GitHub tetap sebagai cadangan. Migrasi tidak diterapkan ke basis data hidup dari tiket ini.
- Berkas:
  - `supabase/migrations/20261027_overlay_live_pg_cron.sql` (baru)
  - `.github/workflows/overlay-live-refresh.yml` (hanya komentar: pg_cron primer)
  - `src/lib/overlay-live-pg-cron.test.ts` (baru; kontrak berkas)
  - jurnal ini
  - satu baris `docs/pengembangan/STATUS.md`
- Tidak diubah: env, `vercel.json`, fixture, UI, rute cron, `weather-refresh.yml`, `sipongi-refresh.yml`, migrasi lama.
- Langkah:
  1. `create extension if not exists pg_net` di skema `extensions`, lalu `pg_cron` di skema `pg_catalog` (pola pemasangan Supabase).
  2. Cabut jadwal lama bernama `overlay-live-refresh` bila ada, lalu jadwalkan ulang `*/15 * * * *`.
  3. Perintah job membaca `select decrypted_secret from vault.decrypted_secrets where name = 'overlay_cron_secret'` saat jalan. Header `Authorization: Bearer` memakai nilai itu. Tidak ada rahasia di berkas.
  4. Jika baris Vault kosong, null, atau hanya spasi, job kembali tanpa `net.http_post`.
  5. `timeout_milliseconds` 70000, di atas `maxDuration` rute (60 detik) dan di bawah batas panduan cron Supabase (10 menit). Bawaan `pg_net` di dokumen saat ini 2000 ms; itu memutus klien sebelum rute selesai.
- Cara membuktikan: uji kontrak berkas; `tsc`, `lint`, `build`, `npm test`. Tidak ada `supabase db push`, SQL editor produksi, atau POST ke cron.
- Risiko: Job dan Actions bisa jalan bersamaan. Refresh menimpa baris live; bukan migrasi data. `pg_net` sempat menulis header (termasuk Bearer) di `net.http_request_queue` sampai permintaan terkirim. Jangan SELECT antrean itu ke log. `docs/vercel.md` bagian 4 masih menyebut cron overlay tetap di GitHub Actions; berkas itu di luar tiket ini.

## Langkah manual pemilik

Satu langkah, di luar git. Jangan tempel nilainya di chat, PR, atau jurnal.

1. Buka Supabase Dashboard proyek produksi, lalu **Vault**.
2. Tambah secret. **Name** persis `overlay_cron_secret`.
3. **Value** = nilai yang sama dengan env Vercel `OVERLAY_CRON_SECRET` (Production). Salin dari pengaturan env Vercel ke Vault. Jangan kirim nilai itu ke siapa pun lewat chat.
4. Boleh dilakukan sebelum atau sesudah GO. Backend menerapkan migrasi `20261027_overlay_live_pg_cron.sql` nanti, setelah GO. Tiket ini tidak menerapkan apa pun ke basis data hidup.
5. Sebelum secret ada, job (kalau migrasi sudah hidup) selesai tanpa HTTP. Workflow GitHub tetap cadangan selama itu.

## Verifikasi setelah Backend menerapkan

Jangan SELECT `net.http_request_queue`. Antrean itu dapat memuat header `Authorization` sampai permintaan terkirim. Jangan salin `command` ke chat bila Anda tidak perlu; perintah hanya berisi SQL pembaca Vault, bukan nilai secret.

```sql
select jobid, jobname, schedule, active
from cron.job
where jobname = 'overlay-live-refresh';
```

Harapan: satu baris, `schedule` = `*/15 * * * *`, `active` = true.

```sql
select start_time, end_time, status, return_message
from cron.job_run_details
where jobid = (
  select jobid from cron.job where jobname = 'overlay-live-refresh'
)
order by start_time desc
limit 8;
```

Harapan: `status` succeeded kira-kira tiap 15 menit. Run sukses saat secret belum ada juga succeeded, karena blok kembali tanpa HTTP. Itu belum membuktikan kartu disegarkan.

```sql
select id, status_code, timed_out, error_msg, created
from net._http_response
order by created desc
limit 8;
```

Setelah secret Vault ada: dalam satu siklus 15 menit ada baris `status_code` 200, `timed_out` false. `content` adalah JSON rute (`refreshed`, `failed`, `layers`) dan tidak memuat Bearer; tetap jangan tempel ke chat.

```sql
select layer_key, refreshed_at, ok, feature_count
from public.overlay_live_refresh
order by layer_key;
```

`refreshed_at` maju kira-kira tiap 15 menit setelah job dan secret sama-sama hidup. Bandingkan dua pembacaan berjarak 15–20 menit.

```sql
select cron.unschedule(jobid)
from cron.job
where jobname = 'overlay-live-refresh';
```

## Cuaca dan Sipongi

Keduanya tidak diubah.

`weather-refresh.yml` menjadwalkan `0 */3 * * *` (tiap 3 jam UTC), plus `workflow_dispatch`. Job `refresh-snapshot` meng-commit fixture dan tidak punya TTL 2 jam. Job `refresh-supabase` POST ke `vars.WEATHER_REFRESH_URL` bila variabel itu terisi. `POST /api/weather/refresh` menulis `expires_at` = sekarang + 2 jam, jendela yang sama dengan `OVERLAY_WEATHER_LIKE_TTL_MS`. Pembaca `loadFromSupabase` di `src/lib/weather/service.ts` mengambil baris tanpa menyaring `expires_at`; jika ada sedikitnya 20 kabupaten, cache itu yang dikembalikan, lalu cadangan cache Next 1 jam dan fixture. Keterlambatan GitHub 2–6 jam membuat data lebih tua dari jadwal 3 jam, dan TTL tertulis 2 jam sudah lebih pendek dari jadwal nominal. Kartu cuaca tidak ikut pola overlay yang menjadi tidak tersedia saat `expires_at` lewat, karena pembaca tidak menolak baris kedaluwarsa. Mekanisme telatnya sama. Bentuk gangguan kartunya tidak sama.

`sipongi-refresh.yml` menjadwalkan `30 2 * * 1-5` (hari kerja 09:30 WIB). Ia meng-commit `public/fixtures/peringatan-sipongi.json`. Tidak ada `expires_at` dan tidak ada POST cron. Telat 2–6 jam hanya menggeser jam commit; fixture sebelumnya tetap di git. Kartu Sipongi hidup dibaca dari overlay `sipongiHotspots` (`getSipongiPeringatan`), jadi TTL 2 jam overlay — itu job yang tiket ini pindahkan ke `pg_cron`. Fixture hanya cadangan bila baca overlay tidak bisa atau melempar, dan ditandai `stale`, `source: "fixture"`, `example: true`. Mekanisme telat GitHub ada. Celah “habis 2 jam lalu kartu live mati di antara `*/15`” tidak ada pada workflow fixture ini.
